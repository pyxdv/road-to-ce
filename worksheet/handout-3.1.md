# ส่วนที่ 1 · กลไกของอินเทอร์เน็ต

## 1. Client และ Server

บริการออนไลน์แทบทั้งหมด ไม่ว่าจะเป็นเว็บ อีเมล เกมออนไลน์ หรือแอปธนาคาร ทำงานบนรูปแบบเดียวกัน

| บทบาท | หน้าที่ |
|---|---|
| **Client** (เครื่องผู้ขอ) | เครื่องที่เริ่มต้นขอข้อมูล เช่น browser บนคอมพิวเตอร์หรือมือถือ |
| **Server** (เครื่องผู้ให้บริการ) | เครื่องที่เปิดรอรับคำขอตลอดเวลา เมื่อมีคำขอเข้ามาก็ส่งข้อมูลกลับไป |

เมื่อพิมพ์ URL แล้วกด Enter browser (client) จะส่ง request ไปหา server แล้ว server ส่ง response กลับมา
จากนั้น browser จึงนำข้อมูลที่ได้มาแสดงผลเป็นหน้าเว็บ

> **ข้อสังเกต** server ไม่ได้ส่งข้อมูลมาให้เองโดยที่เราไม่ได้ขอ ทุกอย่างเริ่มจากฝั่ง client เสมอ
> นี่คือเหตุผลที่หน้าเว็บจะไม่อัปเดตตัวเองถ้าไม่กด refresh และเป็นเหตุผลที่เทคนิคอย่าง
> WebSocket ถูกคิดขึ้นมาในภายหลัง

## 2. Domain name และ IP address

คอมพิวเตอร์บนอินเทอร์เน็ตไม่ได้ติดต่อกันด้วยชื่อ แต่ติดต่อกันด้วย **IP address** ซึ่งเป็นตัวเลขประจำเครื่อง
เช่น `185.199.108.153` ส่วนชื่ออย่าง `rmuti.ac.th` มีไว้ให้มนุษย์จำ

**DNS (Domain Name System)** คือระบบที่แปลงชื่อโดเมนเป็น IP address ก่อนที่ browser จะติดต่อ
กับ server ได้ ต้องถาม DNS ก่อนเสมอ กระบวนการนี้เร็วมากจนผู้ใช้ไม่รู้สึก แต่ถ้า DNS ล่ม
เว็บทั้งอินเทอร์เน็ตจะเข้าไม่ได้ ทั้งที่ตัว server ยังทำงานปกติ

**ทำไมไม่ใช้ IP address ตรง ๆ**

- มนุษย์จำชื่อได้ดีกว่าจำตัวเลข
- เจ้าของเว็บย้ายเครื่องหรือเปลี่ยนผู้ให้บริการได้ โดยที่ชื่อโดเมนยังเหมือนเดิม
- ชื่อเดียวชี้ไปหลาย IP address ได้ ทำให้กระจายภาระงานและตั้ง server หลายที่ทั่วโลกได้

ตรวจสอบเองได้ด้วยคำสั่ง `nslookup <ชื่อโดเมน>`

## 3. HTTP — ภาษาที่ client กับ server ใช้คุยกัน

เมื่อรู้ IP address แล้ว browser จะส่ง HTTP request ไปยัง server ตามรูปแบบที่ตกลงกันไว้
และ server จะตอบกลับเป็น HTTP response ทั้งสองฝั่งต้องใช้รูปแบบเดียวกัน จึงเรียกว่า
**protocol** (ข้อตกลงในการสื่อสาร)

|  | Request (จาก client) | Response (จาก server) |
|---|---|---|
| บรรทัดแรก | method + path เช่น `GET /index.html` | status code เช่น `200 OK` |
| ส่วนถัดมา | headers บอกรายละเอียด | headers เช่น `content-type` แล้วตามด้วย body คือเนื้อหาไฟล์จริง |

### Status code ที่ควรจำ

| รหัส | ความหมาย | เจอตอนไหน |
|---|---|---|
| `200` | OK สำเร็จ | ปกติที่สุด server ส่งไฟล์ที่ขอกลับมาครบ |
| `301` / `302` | Redirect ย้ายที่อยู่ | server บอกให้ไปขอที่ URL อื่นแทน |
| `304` | Not Modified | ไฟล์ไม่เปลี่ยนตั้งแต่ครั้งก่อน browser ใช้ของใน cache ได้ |
| `403` | Forbidden | ไฟล์มีอยู่ แต่ไม่มีสิทธิ์เข้าถึง |
| `404` | Not Found | ไม่พบไฟล์ที่ขอ มักเกิดจากพิมพ์ path ผิดหรือไฟล์ถูกลบ |
| `500` | Internal Server Error | server ทำงานผิดพลาดเอง ไม่ใช่ความผิดของฝั่งผู้ขอ |

> **หลักการอ่าน status code** ตัวเลขหลักแรกบอกประเภทของคำตอบ `2xx` สำเร็จ · `3xx` ให้ไปที่อื่น ·
> `4xx` ฝั่งผู้ขอผิดพลาด · `5xx` ฝั่ง server ผิดพลาด จำหลักนี้ไว้จะเดาความหมายของรหัสที่ไม่เคยเห็นได้

### เวอร์ชันของ HTTP

HTTP/1.1 ใช้กันมานาน ข้อจำกัดคือหนึ่งการเชื่อมต่อส่งได้ทีละไฟล์ ต่อมา **HTTP/2** (`h2`)
ส่งหลายไฟล์พร้อมกันในการเชื่อมต่อเดียวได้ และ **HTTP/3** (`h3`) ปรับให้ทนต่อสัญญาณที่ไม่เสถียร
เช่นการใช้งานผ่านมือถือได้ดีขึ้น ดูได้จากคอลัมน์ Protocol ใน DevTools

## 4. HTTPS, TLS และ certificate

HTTP ธรรมดาส่งข้อมูลเป็นข้อความที่อ่านได้ทันที ใครที่อยู่ระหว่างทาง เช่น ผู้ให้บริการเครือข่าย
หรือคนที่ใช้ Wi-Fi สาธารณะร่วมกัน สามารถดักอ่านหรือแก้ไขข้อมูลได้
HTTPS แก้ปัญหานี้ด้วยการเพิ่ม **TLS (Transport Layer Security)** เข้าไปอีกชั้น

TLS ทำสองอย่างพร้อมกัน

1. **เข้ารหัสข้อมูล** ทำให้คนที่ดักกลางทางเห็นเป็นข้อมูลที่อ่านไม่ออก
2. **ยืนยันตัวตนของ server** ว่าเป็นเจ้าของโดเมนนั้นจริง ไม่ใช่เครื่องปลอมที่แอบสวมรอย

การยืนยันตัวตนทำผ่าน **certificate** (ใบรับรองดิจิทัล) ที่ออกโดย **Certificate Authority (CA)**
เมื่อ browser ได้รับ certificate จะตรวจว่า CA ที่ออกให้เชื่อถือได้ certificate ยังไม่หมดอายุ
และชื่อโดเมนใน certificate ตรงกับที่กำลังเปิดอยู่ ถ้าข้อใดไม่ผ่าน browser จะขึ้นคำเตือนเต็มหน้าจอ

คลิกที่รูปกุญแจข้างช่อง URL เพื่อดู certificate ของเว็บที่กำลังเปิดอยู่ได้ทุกเว็บ

## 5. Latency — ทำไมระยะทางจึงมีผลต่อความเร็ว

สัญญาณข้อมูลเดินทางเร็วมาก แต่ไม่ได้เร็วอย่างไม่มีขีดจำกัด แสงในสาย fiber optic
เดินทางได้ประมาณ **200 กิโลเมตรต่อ 1 มิลลิวินาที** ตัวเลขนี้เป็นเพดานทางฟิสิกส์

**RTT (Round-Trip Time)** คือเวลาที่สัญญาณใช้เดินทางไปถึงปลายทางและกลับมา วัดได้ด้วยคำสั่ง `ping`
เนื่องจากเป็นเวลาไปและกลับ การประมาณระยะทางจึงต้องหารสอง

> **ตัวอย่าง** ถ้า `ping` ได้ RTT 30 ms ระยะทางที่สัญญาณวิ่งรวมไปและกลับคือ
> 30 × 200 = 6,000 กิโลเมตร ดังนั้น server อยู่ห่างประมาณ **3,000 กิโลเมตร**

ค่าที่วัดได้จริงจะสูงกว่าการคำนวณเสมอ เพราะข้อมูลไม่ได้วิ่งเป็นเส้นตรง และต้องผ่านอุปกรณ์เครือข่าย
หลายตัวระหว่างทาง

**TTFB (Time To First Byte)** คือเวลาตั้งแต่ส่ง request จนได้รับข้อมูลไบต์แรกกลับมา สะท้อนทั้งระยะทาง
และความเร็วในการประมวลผลของ server รวมกัน วิธีลด TTFB ที่ได้ผลที่สุดคือย้าย server ให้ใกล้ผู้ใช้
ซึ่งเป็นแนวคิดของ **CDN (Content Delivery Network)** ที่กระจายสำเนาเว็บไซต์ไปเก็บตามเมืองใหญ่ทั่วโลก
GitHub Pages ก็ใช้ CDN เช่นกัน

## 6. Web hosting และ static site

การจะให้เว็บไซต์เปิดได้จากทุกที่ ไฟล์ต้องอยู่บนเครื่องที่เปิดตลอดเวลาและเชื่อมต่ออินเทอร์เน็ต
การฝากไฟล์ไว้บนเครื่องแบบนี้เรียกว่า **hosting**

| ประเภท | ลักษณะ |
|---|---|
| **Static site** | server ส่งไฟล์ที่เตรียมไว้ล่วงหน้ากลับไปตรง ๆ ทุกคนได้หน้าตาเหมือนกัน เร็ว ราคาถูก และแทบไม่มีช่องโหว่ให้โจมตี |
| **Dynamic site** | server ประมวลผลและสร้างหน้าเว็บขึ้นใหม่ทุกครั้ง เช่น หน้า feed ของ social media ที่แต่ละคนเห็นไม่เหมือนกัน |

**GitHub Pages** เป็นบริการ hosting สำหรับ static site ที่ให้ใช้ฟรี เมื่อเก็บไฟล์ HTML ไว้ใน repository
และเปิดใช้งาน Pages ระบบจะนำไฟล์ไปวางบน server แล้วให้ URL มาใช้งาน ทุกครั้งที่แก้ไฟล์
ระบบจะอัปเดตเว็บให้เองภายในไม่กี่นาที

- repository ชื่อ `<username>.github.io` จะได้ URL หลักคือ `https://<username>.github.io`
- ไฟล์ชื่อ `index.html` เป็นไฟล์พิเศษ เพราะ server จะส่งไฟล์นี้ให้เมื่อมีคนเปิด URL โดยไม่ระบุชื่อไฟล์
  ซึ่งเป็นข้อตกลงที่ web server แทบทุกตัวใช้เหมือนกัน
- repository ต้องตั้งเป็น Public จึงจะใช้ GitHub Pages ได้ในบัญชีแบบไม่เสียค่าใช้จ่าย

> **สังเกตให้ดีตอนทำใบงาน** ทุกครั้งที่กด Commit changes จะมีระบบเบื้องหลังตื่นขึ้นมานำไฟล์ใหม่
> ไปวางบน server ให้เองภายในไม่กี่นาที โดยไม่มีคนมาแตะ กระบวนการแบบนี้เรียกว่า **CI/CD**
> ซึ่งทีมพัฒนาซอฟต์แวร์ทั่วโลกใช้ทำงานทุกวัน จะได้เรียนละเอียดในรายวิชาปีถัดไป

# ส่วนที่ 2 · การสร้างตัวตนออนไลน์ในฐานะวิศวกร

## 7. Git และ GitHub เท่าที่ต้องใช้ในใบงานนี้

**Git** เป็นโปรแกรมสำหรับเก็บประวัติการแก้ไขไฟล์ ส่วน **GitHub** เป็นบริการออนไลน์ที่เก็บงานที่ใช้ Git
ไว้บนอินเทอร์เน็ตและเพิ่มเครื่องมือสำหรับทำงานร่วมกัน ทั้งสองอย่างเป็นคนละสิ่งกัน

ในใบงานนี้ใช้เพียงสามคำ เท่านี้พอสำหรับการนำเว็บขึ้นใช้งาน

| คำศัพท์ | ความหมาย |
|---|---|
| **Repository (repo)** | พื้นที่เก็บงานหนึ่งชุด รวมไฟล์ทั้งหมดและประวัติการแก้ไขทุกครั้ง |
| **Commit** | การบันทึกสถานะของไฟล์ ณ จุดหนึ่ง พร้อมข้อความอธิบายว่าแก้อะไร ทุก commit ย้อนกลับไปดูหรือกู้คืนได้เสมอ ทำให้ทดลองแก้ได้โดยไม่ต้องกลัวพัง |
| **README.md** | ไฟล์แนะนำ repository ที่ GitHub จะนำมาแสดงบนหน้าแรกของ repo นั้นให้อัตโนมัติ |

> **รู้ไว้ก่อน จะได้ใช้จริงในรายวิชาปีถัดไป** เมื่อทำงานกันเป็นทีม จะมีอีกสามคำที่ต้องรู้คือ
> **branch** (สายการพัฒนาที่แยกออกมาทดลองแก้) · **Pull Request** (การเสนอให้นำงานของเรารวมเข้ากับสายหลัก)
> · **code review** (การที่เพื่อนร่วมทีมอ่านงานแล้วให้ข้อเสนอแนะก่อนรวมงาน)
> สามคำนี้เป็นหัวใจของการทำงานเป็นทีม แต่ยังไม่ต้องใช้ในใบงานนี้
> ตอนนี้ขอให้คุ้นกับ repository และ commit ให้ดีเสียก่อน

## 8. เนื้อหาอะไรควรอยู่บนเว็บส่วนตัว

คำถามที่ยากที่สุดสำหรับนักศึกษาปี 1 ไม่ใช่ทำเว็บอย่างไร แต่คือจะเอาอะไรใส่ลงไปในเมื่อยังไม่มีผลงาน

คำตอบคือ **เว็บของนักศึกษาปี 1 ไม่ได้มีไว้อวดผลงาน แต่มีไว้แสดงว่าเรากำลังเดินไปทางไหน**

### ห้าส่วนที่ควรมี

| ส่วน | ใส่อะไร |
|---|---|
| 1. เราคือใคร | ชื่อที่ใช้แสดง ระดับชั้น สาขา สถาบัน สั้น ๆ |
| 2. สนใจสร้างอะไร | หนึ่งประโยคที่เจาะจง เป็นส่วนที่คนอ่านจำได้มากที่สุด |
| 3. กำลังเรียนรู้อะไร | รายการสั้น ๆ ของสิ่งที่กำลังเรียนอยู่จริง ส่วนนี้จะเปลี่ยนไปทุกภาคเรียน และเป็นสิ่งที่แสดงว่าเราไม่หยุดนิ่ง |
| 4. ผลงาน | ยังว่างได้ ให้เขียนกำกับตามจริงว่ากำลังสะสม เมื่อมีงานแล้วค่อยเพิ่มทีละชิ้น พร้อมคำอธิบายว่าทำอะไรและใช้อะไรทำ |
| 5. ติดต่ออย่างไร | ใช้ลิงก์สาธารณะเท่านั้น เช่น หน้า GitHub **ห้ามใส่เบอร์โทรศัพท์หรืออีเมลส่วนตัว** |

### การเขียนหนึ่งประโยคแนะนำตัว (tagline)

ประโยคที่ดีต้องเจาะจงจนคนอ่านนึกภาพออก ประโยคที่กว้างเกินไปจะไม่ต่างจากคนอื่นเลย

| เขียนแบบนี้ยังกว้างไป | เขียนแบบนี้คนจำได้ |
|---|---|
| รักการเขียนโปรแกรมและเทคโนโลยี | อยากทำระบบรดน้ำต้นไม้ที่ดูพยากรณ์อากาศก่อนตัดสินใจรด |
| สนใจด้าน IoT และ AI | อยากรู้ว่าจะทำให้บอร์ดราคาสองร้อยบาทแจ้งเตือนเข้ามือถือได้อย่างไร |
| ตั้งใจเรียนและพัฒนาตัวเอง | กำลังหัดเขียนเว็บ เป้าหมายภาคเรียนนี้คือทำหน้าเว็บที่ใช้งานได้จริง |

> **หลักที่ใช้ได้ตลอด** เขียนตามจริงว่าอยู่จุดไหน ดูน่าเชื่อถือกว่าเขียนเกินตัวเสมอ

> ไม่ใช่รายการทักษะที่ยาวเกินจริง

## 9. หลักการออกแบบหน้าเว็บให้อ่านง่ายและดูดี

การทำหน้าเว็บให้ดูดีไม่ได้ต้องใช้พรสวรรค์ด้านศิลปะ แต่ใช้กฎไม่กี่ข้อที่ทำตามได้ทันที
ข้อผิดพลาดของมือใหม่แทบทั้งหมดมาจากการละเมิดกฎหกข้อนี้

| หลักการ | รายละเอียด |
|---|---|
| **1. ลำดับความสำคัญ** | ขนาดตัวอักษรต้องต่างกันให้ชัด ชื่อควรใหญ่กว่าเนื้อความอย่างน้อยสองเท่า ถ้าทุกอย่างขนาดเท่ากันหมด สายตาจะไม่รู้ว่าควรอ่านอะไรก่อน |
| **2. ที่ว่าง** | ข้อผิดพลาดอันดับหนึ่งของมือใหม่คือใส่ของแน่นเกินไป ที่ว่างรอบข้อความทำให้อ่านง่ายขึ้นมากและดูเป็นมืออาชีพขึ้นทันที เว้นระยะระหว่างหัวข้อให้เยอะกว่าที่คิด |
| **3. จำนวนสี** | ใช้สีเน้นเพียงหนึ่งสี ที่เหลือเป็นสีเทาอ่อนแก่ หน้าเว็บที่มีห้าสีจะดูรก ส่วนหน้าเว็บที่มีสีเน้นสีเดียวจะดูตั้งใจออกแบบ |
| **4. ความกว้างบรรทัด** | บรรทัดที่ยาวเกินไปทำให้ตาไล่กลับมาต้นบรรทัดถัดไปไม่ถูก ความกว้างที่อ่านสบายคือประมาณ 50–75 ตัวอักษรต่อบรรทัด |
| **5. ความต่างของสีพื้นกับตัวอักษร** | ตัวอักษรสีเทาอ่อนบนพื้นขาวอ่านยากมากบนจอสว่างหรือกลางแดด ตัวอักษรหลักควรมีความต่างจากพื้นหลังชัดเจน |
| **6. ฟอนต์** | ใช้หนึ่งถึงสองแบบพอ มากกว่านั้นจะดูไม่เป็นระเบียบ และควรใช้ฟอนต์ที่รองรับภาษาไทยได้ครบ |

### ตรวจงานตัวเองก่อนส่ง

- ย่อหน้าต่างเบราว์เซอร์ให้แคบเท่าจอมือถือ ข้อความยังอ่านได้และไม่ล้นออกนอกจอหรือไม่
- ถอยห่างจากจอสองเมตรแล้วมองกลับมา ยังบอกได้ไหมว่าส่วนไหนสำคัญที่สุด
- ให้เพื่อนที่ไม่รู้จักงานเราอ่าน 10 วินาที แล้วถามว่าจำอะไรได้บ้าง

> **ข้อคิดสำหรับวิศวกร** หน้าเว็บที่อ่านง่ายไม่ได้เกิดจากการเพิ่มของ แต่เกิดจากการเอาของที่ไม่จำเป็นออก
> หลักการเดียวกันนี้ใช้ได้กับการเขียนโค้ด การเขียนรายงาน และการนำเสนองาน

## 11. Digital footprint และความเป็นส่วนตัว

ข้อมูลที่เผยแพร่บนอินเทอร์เน็ตสาธารณะจะถูกค้นหาเจอโดย search engine และมักถูกเก็บสำเนาไว้
โดยระบบอื่น เช่น web archive หรือ cache ของ search engine ผลคือแม้จะลบต้นฉบับออกไปแล้ว
สำเนายังอาจอยู่ต่อไปอีกนาน จึงควรพิจารณาให้รอบคอบ **ก่อน** เผยแพร่

**ข้อมูลที่ไม่ควรเผยแพร่บนพื้นที่สาธารณะ**

- เลขประจำตัวประชาชน เลขหนังสือเดินทาง เลขบัญชีธนาคาร
- เบอร์โทรศัพท์ส่วนตัว ที่อยู่ที่พักอาศัย
- ภาพบัตรประจำตัวหรือเอกสารราชการทุกชนิด
- ข้อมูลที่ทำให้คาดเดาได้ว่าเราอยู่ที่ใดในแต่ละช่วงเวลา เช่น ตารางเรียนที่ระบุห้องและเวลา
- ข้อมูลของผู้อื่นที่เจ้าตัวไม่ได้อนุญาต เช่น ภาพถ่ายเพื่อนหรือรายชื่อสมาชิกกลุ่ม

การใช้ชื่อเล่นหรือชื่อที่ตั้งขึ้นสำหรับแสดงต่อสาธารณะ แทนชื่อ-นามสกุลเต็มคู่กับรหัสนักศึกษา
เป็นวิธีที่ง่ายที่สุดในการลดความเสี่ยง โดยที่ยังแสดงผลงานได้เหมือนเดิม

การเผยแพร่ข้อมูลส่วนบุคคลของผู้อื่นโดยไม่ได้รับความยินยอม เข้าข่ายความผิดตาม
**พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA)** ซึ่งบังคับใช้กับทุกคน

## 12. ตารางศัพท์เทคนิค

| ศัพท์ | คำไทยที่ใช้คู่กัน | ความหมายโดยย่อ |

| Server | เครื่องผู้ให้บริการ | ฝ่ายที่เปิดรอรับคำขอและส่งข้อมูลกลับ |

| IP address | หมายเลขไอพี | ตัวเลขประจำเครื่องบนเครือข่าย |
| DNS | ระบบชื่อโดเมน | ระบบที่แปลงชื่อโดเมนเป็น IP address |
| Protocol | โพรโทคอล | ข้อตกลงรูปแบบการสื่อสารระหว่างสองฝ่าย |

| Certificate | ใบรับรองดิจิทัล | เอกสารยืนยันว่า server เป็นเจ้าของโดเมนนั้นจริง |
| Status code | รหัสสถานะ | ตัวเลขที่ server ใช้บอกผลของคำขอ |
| Cache | หน่วยความจำพัก | การเก็บข้อมูลที่เคยได้มาแล้วไว้ใช้ซ้ำ |
| Latency / RTT | ความหน่วง | เวลาที่ข้อมูลใช้เดินทางไปและกลับ |
| CDN | เครือข่ายกระจายเนื้อหา | ระบบกระจายสำเนาเว็บไปเก็บใกล้ผู้ใช้ทั่วโลก |
| Hosting | การฝากเว็บ | การนำไฟล์เว็บไปวางบนเครื่องที่เปิดตลอดเวลา |
| Static site | เว็บแบบคงที่ | เว็บที่ส่งไฟล์สำเร็จรูปกลับไปตรง ๆ |
| Repository | แหล่งเก็บงาน | พื้นที่เก็บไฟล์พร้อมประวัติการแก้ไข |
| Commit | การบันทึกเวอร์ชัน | การบันทึกสถานะไฟล์พร้อมข้อความอธิบาย |
| Branch | สายการพัฒนา | สายงานที่แยกออกมาทดลองแก้ไข |
| README | ไฟล์แนะนำ | ไฟล์ที่ GitHub นำมาแสดงบนหน้าแรกของ repository |
| Profile README | ไฟล์แนะนำตัว | README ใน repo ชื่อเดียวกับ username จะขึ้นบนหน้า profile |
| CI/CD | ระบบอัตโนมัติ | ระบบที่ตรวจและนำงานขึ้นใช้งานให้เองเมื่อมีการแก้ไข |

## 13. คำถามทบทวน

ตอบด้วยตนเองก่อนเข้าคาบ ไม่ต้องส่ง

1. ถ้า DNS ทั้งระบบหยุดทำงาน แต่ server ของเว็บยังทำงานปกติ ผู้ใช้จะยังเปิดเว็บได้หรือไม่ เพราะอะไร
2. status code `404` กับ `500` บอกคนละเรื่องกันอย่างไร และแต่ละกรณีควรไปแก้ที่ฝั่งใด
3. เว็บที่ใช้ HTTP ธรรมดา มีความเสี่ยงอะไรบ้างเมื่อใช้งานผ่าน Wi-Fi สาธารณะ
4. ถ้า `ping` ไปยัง server แห่งหนึ่งได้ค่า RTT 80 ms server นั้นน่าจะอยู่ห่างประมาณกี่กิโลเมตร
5. ทำไมไฟล์ชื่อ `index.html` จึงเป็นไฟล์พิเศษสำหรับ web server
6. ลองเขียนหนึ่งประโยคแนะนำตัวของตนเองสองแบบ แบบกว้างและแบบเจาะจง แล้วเปรียบเทียบว่าต่างกันอย่างไร
7. เปิดเว็บที่ตนเองคิดว่าออกแบบดี แล้ววิเคราะห์ว่าใช้กฎข้อใดในหัวข้อ 9 บ้าง
8. ข้อมูลใดบ้างในโปรไฟล์ social media ของตนเองในปัจจุบัน ที่ตามหลักในหัวข้อ 11 แล้วไม่ควรเปิดสาธารณะ
